# 3rd Eye Supply — agent service skeleton (B1, fixed per review 2026-10-27)

## Boundary — what this skeleton deliberately does NOT do

No real LLM calls, no live n8n calls, no agent logic — that is B2's leg.
The `/agent/run` executor is a stub that returns `agent_logic:
"not_implemented"` honestly, and the endpoint reports it with
`status: "stub"` — never `"complete"` (B1-3). Nothing here has been
deployed or proven live; these fixes are "fixed per review, awaiting
re-review + QA re-run."

## Architecture (as briefed)

n8n stays the ACTION layer (webhooks, schedules, API calls, integrations,
the fulfilment pipe). This service is the BRAIN layer: LangChain/LangGraph
agents, triggered by n8n, calling back into n8n workflows as tools (n8n
webhooks become the agent's hands). Adversarial verdict and reasoning are
recorded on issue #126 before any code was written.

## Wiring-seam owner (reviewer's design question — decided)

B1 OWNS checkpoint creation and tool execution. B2's langgraph_adapter
CONSUMES them (checkpointer argument, scouts wired to `execute_tool`).
There is exactly one integration shape; a second one is a defect.

## How n8n triggers it

n8n HTTP Request node → `POST {SERVICE_URL}/agent/run` with:

- Header `X-Agent-Shared-Secret: <AGENT_SHARED_SECRET>` (see env vars).
  Bad or missing secret → `401`, attempt logged, secret never logged.
  Unset `AGENT_SHARED_SECRET` → `401` always (fail closed).
- JSON body: `{"run_id": "<UUIDv4>", "input": {...}}`.
- `run_id` is the idempotency key AND must be an unguessable UUIDv4
  generated by n8n (F-B1-1; anything else → `422`). A duplicate `run_id`
  with the SAME input returns the existing result and never re-executes
  — including after a failure, which is recorded, not silently retried.
  A duplicate `run_id` with DIFFERENT input → `409` with NO stored
  result or input in the body.
- Response `status`: `"complete"` (real run), `"stub"` (skeleton
  executor, no agent logic ran), `"failed"` (executor failed; the
  failure is recorded and a duplicate returns the same failure).

## Trust boundary (F-B1-1, F-B1-6)

- The ONLY secret holder is n8n. The service is reachable ONLY on the
  private network between n8n and this service — never exposed publicly.
  There is no per-caller ownership on run records: any secret holder can
  replay a run_id, which is why run_ids must be unguessable UUIDv4s.
- `/health` is intentionally unauthenticated: a liveness probe only,
  returning no data about runs, config, or credentials.
- Rate limiting and body-size limits are NOT in this code — they are
  DEPLOYMENT controls: the reverse proxy in front of this service (on
  the private network) must enforce them before any wider exposure.
- Env vars are OPERATOR-CONTROLLED TRUSTED INPUT (B1-4): only the
  service operator may write the process environment. Tool URLs are
  still validated at execution (below); validation does not replace
  restricting env write access.

## Env vars (secrets = env vars ONLY, never in code)

| Var | Purpose |
| --- | ------- |
| `AGENT_SHARED_SECRET` | Shared secret n8n presents in `X-Agent-Shared-Secret` |
| `DATABASE_URL` | Postgres DSN for LangGraph PostgresSaver checkpointing |
| `DB_POOL_MIN_SIZE` / `DB_POOL_MAX_SIZE` | Checkpoint POOL bounds (defaults 1 / 10) — honoured for real: passed to a psycopg_pool ConnectionPool given to PostgresSaver (B1-1) |
| `N8N_TOOL_<NAME>_URL` | One tool per var, e.g. `N8N_TOOL_NOTIFY_URL` → tool `notify`; must be https (non-https fails at registry build) |
| `N8N_TOOL_<NAME>_AUTH` | Per-tool Authorization header value (F-B1-5); env only, never logged |
| `N8N_TOOL_<NAME>_IDEMPOTENT` | `"true"` ONLY when the operator has verified with the webhook owner that the target honours `X-Idempotency-Key` for dedupe; gates timeout AND 5xx retries (F-B1-4, R-B1-3) |
| `N8N_ALLOWED_HOSTS` | REQUIRED comma-separated tool-host allowlist (F-B1-2, R-B1-1); registry build fails closed if unset/empty, and every registry tool inherits it. `execute_tool` with no allowlist (explicit arg or tool-carried) refuses before any HTTP. Corrects the earlier "optional" wording, which was false: no code path enforced an unset allowlist. |

All values in this repo's examples are obviously fake placeholders.

## Checkpointing (B1-1)

- Default path: pooled PostgresSaver — `build_postgres_saver` builds a
  `psycopg_pool.ConnectionPool` with the env pool bounds and passes it
  to the installed langgraph-checkpoint-postgres 2.0.16 PostgresSaver
  (which accepts a pool, not only a single connection).
  `PostgresSaver.from_conn_string` is the SINGLE-connection path (it
  returns a context manager, not a saver, and honours no pool bounds)
  and is NOT the default here.
- REQUIRED FIRST-USE STEP: the wiring leg must open the pool and call
  `setup_postgres_saver(saver)` ONCE before the first graph invocation
  — it creates/migrates the checkpoint tables, and first real
  checkpoint use fails without it. It is deliberately not hidden in
  construction or import.
- Pool lifecycle (wiring leg owns it): open at startup, `setup()` once,
  close at shutdown.

## Tool execution (B1-4, B1-5, F-B1-2, F-B1-4, F-B1-5, F-B1-7, R-B1-1..R-B1-3)

- URL validation before any HTTP: https only, REQUIRED allowlist
  (see env table; unset = fail closed), and after DNS resolution
  every address is checked. A NON-allowlisted host must resolve ONLY
  to global addresses (`is_global`) — that covers private / loopback /
  link-local (incl. cloud metadata 169.254.169.254) / multicast /
  reserved / unspecified AND shared address space 100.64.0.0/10, which
  the old category enumeration missed. An ALLOWLISTED host bypasses
  the global check (this is what lets n8n be reached over Tailscale
  100.x / private ranges — explicitly approved hosts only) but still
  may never resolve to loopback, link-local/metadata, multicast, or
  unspecified. DNS failure fails closed. Registry build checks
  scheme/host/allowlist only (no DNS at startup); `execute_tool`
  always checks DNS.
- TOCTOU residual, stated honestly (R-B1-2): validation DNS and the
  httpx connect DNS are two independent resolutions, so a hostile DNS
  answer could return a public IP at validation time and a private IP
  at connect time. IP pinning (connect to the validated IP with
  TLS/SNI preserved) is NOT implemented — httpx offers no supported
  path for it without a custom transport, and an untested custom
  transport would be a claim, not a control. Compensations: the
  allowlist (only approved hosts, whose DNS is operator-controlled),
  per-tool auth, and private-network-only deployment. IP pinning is a
  named wiring hardening item (see wiring checklist).
- Per-tool auth from env (Authorization header). A tool with no auth
  configured must stay on the private network — its URL is its only
  credential.
- Retries: ONLY for tools flagged idempotent — timeouts AND 5xx
  (default: NOT retried). A non-idempotent timeout raises immediately
  (server-side outcome unknown); a non-idempotent 5xx fails fast with
  a warning log (a 5xx CAN follow a server-side side effect, so the
  old "5xx proves non-success" theory is withdrawn). Never on 4xx.
  Retries back off exponentially from `backoff_seconds` (default 0.5s).
- Input payloads are validated against the tool's `input_schema`
  (`required` + primitive property types); an empty schema validates
  everything.
- A non-JSON 2xx body returns `{"raw_text": ...}` instead of raising.
- A client created inside `execute_tool` is closed before returning; a
  caller-passed client stays the caller's to close.
- In-memory run store limit (B1-2, stated plainly): a process restart
  loses all run records, and duplicates after a restart WILL re-execute.
  Production wiring replaces it with a Postgres-backed store behind the
  same record shape. Do not quote at-most-once across restarts.
- In-memory run store bound (R-B1-4): completion events are pruned
  when a run fills its record (so `_events` does not grow with every
  completed run), and a waiting duplicate times out after
  `wait_timeout_seconds` (default 300s) instead of blocking forever.
  Run records themselves are retained for the process lifetime — they
  ARE the idempotency state; the Postgres-backed store is the wiring
  replacement, not faked here.

## Deployment controls (R-B1-4, F-B1-6)

- Rate limiting and body-size limits are NOT in this code. An example
  reverse-proxy config ships at `deploy/nginx.conf.example` (rate
  limit + `client_max_body_size`, private-interface listen, proxy to
  the app on port 8000). It is an EXAMPLE TO ADAPT, not a deployed
  control: adapting it, pointing it at the real service, and putting
  it in front of the service is a wiring/activation step. The shipped
  `docker-compose.yml` stays a LOCAL-DEV-ONLY snippet (host port
  mappings 8000 + 5432, placeholder credentials, root container user)
  and must not be carried to a real deploy unchanged.

## Wiring checklist (activation — NOT yet evidenced, R-B1-5 + R-B1-4 + R-B1-2)

These are wiring/activation checks, not code defects in this leg.
Each must be evidenced before any wider exposure; none is claimed
done here:

1. n8n UUIDv4 generation (R-B1-5): prove the wiring leg's run_id
   generator emits canonical lowercase UUIDv4 (no braces, no
   uppercase, version 4) — `main.py` enforces exactly that shape and
   returns 422 otherwise, so the first live n8n call gets 422 if the
   generator is wrong. No n8n workflow in scope currently evidences
   a generator; do not claim one exists.
2. IP pinning (R-B1-2): implement validated-IP connection with
   TLS/SNI preserved, or re-accept the TOCTOU residual in writing
   with the allowlist + per-tool auth + private-network compensations.
3. Postgres-backed run store (R-B1-4): replace `InMemoryRunStore`
   behind the same record shape so at-most-once survives restarts.
4. Reverse proxy (R-B1-4): adapt `deploy/nginx.conf.example` to the
   real private network, put it in front of the service, and confirm
   rate + body limits actually reject over-limit requests.
5. Allowlist + secrets in env: `N8N_ALLOWED_HOSTS` set to the approved
   n8n hosts only, `AGENT_SHARED_SECRET` + per-tool auth from env
   only, service reachable only on the private n8n↔service network.

## Run locally

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
AGENT_SHARED_SECRET=dev-only-placeholder DATABASE_URL=postgresql://agent:dev-only-placeholder@localhost:5432/agentdb \
  .venv/bin/uvicorn app.main:app --port 8000
```

Local Postgres only (optional, not needed for tests):

```bash
docker compose up -d db
```

NOTE (B1-6): the compose file maps Postgres to host port 5432 and uses
placeholder credentials, and the Dockerfile runs as root — that is a
LOCAL-DEV-ONLY snippet. Do not carry it to a real deploy unchanged:
production Postgres stays on the private network with no host port
mapping, real credentials from env, and a non-root container user.

## Layout

- `app/main.py` — FastAPI app, `POST /agent/run`, `GET /health`
- `app/security.py` — constant-time shared-secret comparison
- `app/runs.py` — claim-then-fill idempotent run store (in-memory skeleton store)
- `app/tools.py` — n8n-webhook tool registry + validated execution; retry only on 5xx / idempotent timeouts
- `app/checkpoint.py` — pooled PostgresSaver config from env + setup step + memory saver for tests
- `deploy/nginx.conf.example` — reverse-proxy EXAMPLE (rate + body limits) to adapt at wiring time, not a deployed control
- `tests/` — TDD suite (failing tests first for each fix, then green)
